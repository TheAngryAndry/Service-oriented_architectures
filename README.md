# Marketplace: ДЗ 1 → ДЗ 2

Каркас ДЗ 1 без бизнес-логики сохранён в
[коммите 9d9e237](https://github.com/TheAngryAndry/Service-oriented_architectures/tree/9d9e237).
Диаграмма и раздел архитектуры ниже описывают этот этап. Текущая ветка содержит
последовательное развитие проекта для ДЗ 2: Rust + Axum, контракт OpenAPI,
PostgreSQL, Flyway, CRUD товаров, заказы, промокоды, JWT и роли.

В ДЗ 2 Users, Catalog и Orders реализованы как модули одного приложения с одной
БД: задание требует атомарную транзакцию между заказом, остатками и промокодом.

## Запуск

Нужны Docker Engine и Docker Compose v2. Команды из корня репозитория:

```sh
docker compose up --build -d --wait --wait-timeout 180
curl -i http://localhost:8080/health
```

Сначала PostgreSQL становится healthy, затем **Flyway** применяет миграции,
после его успешного завершения запускается API. `/health` проверяет соединение с БД.
Первичная сборка загружает Rust-зависимости и может занять несколько минут.

Сеть Compose использует подсеть `172.18.0.0/16` и Linux-мост `br-soa-hw2`.
При использовании TUN-VPN исключайте из перехвата только внутренние адреса
Docker. Исключение интерфейса целиком отправит внешний трафик контейнеров мимо VPN.

- API: `http://localhost:8080`.
- Контракт: [services/orders/openapi/openapi.json](services/orders/openapi/openapi.json),
  также выдаётся через `GET /openapi.json`; его можно импортировать в Postman.
- Логи: `docker compose logs -f orders`.
- Миграции: `docker compose logs migrate`.
- Остановка с сохранением данных: `docker compose down`.

Настройки берутся из переменных окружения или локального `.env`:
`ORDERS_PORT=8080`, `ORDER_INTERVAL_MINUTES=1` (N, диапазон 0–1440),
`POSTGRES_PASSWORD`, `JWT_SECRET` (минимум 32 байта).
Значения секретов по умолчанию предназначены для локального учебного запуска.
Access token действует 20 минут, refresh token — 14 дней.

## Демонстрация данных

Контракт `/openapi.json` можно импортировать в Postman для запросов к API.
На защите содержимое БД можно показать следующими запросами:

```sh
docker compose exec -T postgres psql -U marketplace -d marketplace -c \
  'SELECT id,name,price,stock,status,seller_id FROM products;'
docker compose exec -T postgres psql -U marketplace -d marketplace -c \
  'SELECT id,user_id,status,total_amount,discount_amount,promo_code_id FROM orders;'
docker compose exec -T postgres psql -U marketplace -d marketplace -c \
  'SELECT order_id,product_id,quantity,price_at_order FROM order_items;'
docker compose exec -T postgres psql -U marketplace -d marketplace -c \
  'SELECT code,current_uses,max_uses FROM promo_codes;'
```

## Контракт и кодогенерация

```sh
# Сборка автоматически генерирует DTO и хэндлеры из OpenAPI:
cargo build --locked --manifest-path services/orders/Cargo.toml
cargo test --locked --manifest-path services/orders/Cargo.toml
cargo clippy --locked --manifest-path services/orders/Cargo.toml --all-targets -- -D warnings
```

Нужен Rust 1.91+ (Docker использует 1.95). `build.rs` — небольшой собственный
генератор поддерживаемого в проекте подмножества OpenAPI 3.0.3. Он создаёт **все
HTTP DTO и Axum-хэндлеры привязки маршрутов** в `target/.../out/api.rs`; результат
подключается через `include!` и исключён из Git. Это не OpenAPI Generator CLI.
OpenAPI — редактируемый источник истины; обратной генерации спецификации из кода нет.

`contract.rs` читает эту же спецификацию и до бизнес-логики проверяет required,
nullable, типы, enum, UUID/date-time/email, длины, диапазоны, multipleOf, pattern,
размеры массивов, path/query и дополнительные поля. Ошибки содержат
`details.violations` с путями полей. `api.rs` связывает сгенерированные маршруты
с реализацией; ручных HTTP DTO нет. JWT claims — внутренняя структура токена.

## API и роли

Для защищённых методов нужен `Authorization: Bearer <access_token>`.
USER/SELLER регистрируются через API; ADMIN назначается явно в БД, затем нужно
снова войти или обновить токены. Роль берётся из подписанного JWT, user_id и
seller_id нельзя передать в теле операции.

| Методы | Доступ и назначение |
| --- | --- |
| `POST /auth/register`, `/auth/login`, `/auth/refresh` | Публичные; refresh одноразовый, при использовании ротируется |
| `GET /products`, `GET /products/{id}` | USER, SELLER, ADMIN; включая архивные товары |
| `POST /products` | SELLER, ADMIN; владельцем становится текущий пользователь |
| `PUT /products/{id}`, `DELETE /products/{id}` | SELLER — свои товары, ADMIN — любые; DELETE архивирует |
| `POST /orders` | USER, ADMIN; заказ оформляется на текущего пользователя |
| `GET /orders/{id}`, `PUT /orders/{id}`, `POST /orders/{id}/cancel` | USER — свои заказы, ADMIN — любые |
| `POST /orders/{id}/status` | ADMIN; последовательное продвижение статуса для демонстрации |
| `POST /promo-codes` | SELLER, ADMIN |

Пагинация: `page=0`, `size=20` по умолчанию, максимум 100.
Фильтры `status` и `category` комбинируются, категория сравнивается точно.
Ответ: `items`, `totalElements`, `page`, `size`.
PUT товара заменяет все обязательные поля, отсутствие description очищает его.

## Бизнес-инварианты

- Порядок создания: лимит CREATE_ORDER → активный заказ → каталог → остатки →
  резервирование → снимки цен → промокод → сохранение и журнал операции.
- Один активный заказ (`CREATED`/`PAYMENT_PENDING`) на пользователя: блокировка
  строки пользователя и частичный уникальный индекс в PostgreSQL.
- Все изменения заказа, остатков, промокода и журнала выполняются в одной
  транзакции. Ошибка откатывает изменения. Товары блокируются `FOR UPDATE`
  в порядке UUID, промокод также блокируется перед проверкой его лимита.
- UPDATE: только CREATED; сначала владелец, затем статус и отдельный лимит
  UPDATE_ORDER. Старый резерв возвращается перед проверкой нового.
- Цена оставшейся позиции сохраняется из snapshot; новая позиция получает
  текущую цену. Изменение цены каталога не меняет существующий заказ.
- Повторение product_id в одном запросе запрещено: 400 с путём поля.
- Денежная арифметика — Decimal, БД — NUMERIC(12,2), JSON — number.
  Входные суммы кратны 0.01; скидка округляется до копеек, половина — вверх.
- PERCENTAGE ≤70 применяется; >70 означает нулевую скидку (полную цену),
  согласно фразе задания «в ином случае цена 100%». FIXED_AMOUNT не больше суммы.
- Обновление с промокодом не расходует его повторно: собственное использование
  вычитается при проверке лимита. Если сумма ниже минимума, связь и скидка
  снимаются, current_uses уменьшается. Истёкший/неактивный промокод даёт 422
  с откатом всего обновления.
- Отмена разрешена из CREATED/PAYMENT_PENDING. Она возвращает остатки и
  использование промокода один раз; повторная отмена даёт 409. Исторические
  суммы и ссылка на промокод сохраняются в отменённом заказе.
- Статусы: CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED.
  Возвратов назад и пропуска состояний нет. Отмена — только через `/cancel`.

## Структура

| Файл/каталог | Назначение |
| --- | --- |
| `services/orders/openapi/openapi.json` | Контракт, DTO, ограничения, роли, каталог ошибок |
| `services/orders/build.rs` | Кодогенерация при каждой необходимой пересборке |
| `services/orders/src/contract.rs` | Валидация из контракта |
| `services/orders/src/api.rs` | Диспетчеризация и JSON-логи, X-Request-Id, маскирование секретов |
| `services/orders/src/auth.rs` | Argon2, JWT, ротация refresh |
| `services/orders/src/catalog.rs` | Товары и создание промокодов |
| `services/orders/src/orders.rs` | Транзакционные бизнес-операции |
| `services/orders/migrations` | Версионированные миграции Flyway |

Логи каждого запроса содержат UUID request_id, method, endpoint, status_code,
duration_ms, user_id (или null), timestamp. Для POST/PUT/DELETE сохраняется
request_body с рекурсивным маскированием password и токенов. Некорректный JSON
не записывается целиком. X-Request-Id возвращается и на ошибках.

## Архитектура ДЗ 1: C4 Container

![C4 Container: архитектура маркетплейса](docs/architecture/container.png)

[Открыть полную диаграмму](docs/architecture/container.png)

Диаграмма уровня C4 Container показывает границу маркетплейса, пользователей,
внешние системы, приложения, брокер и хранилища. У контейнеров указаны название,
тип, технология и ответственность, у связей направление, назначение и протокол.

Модель разделена на два вида: запросы и данные сверху, события через RabbitMQ
снизу. Повторяющиеся сервисы обозначают одни и те же контейнеры. Сплошные линии
показывают синхронные вызовы, пунктир обозначает асинхронные взаимодействия.

### Домены и их ответственность

| Домен | Ответственность |
| --- | --- |
| Пользователи | Регистрация, вход, роли покупателя и продавца, профиль и предпочтения |
| Каталог | Публикация товаров, категории, актуальные цены, остатки и резервирование |
| Персонализированная лента | Ранжирование и выдача товаров по предпочтениям и просмотрам |
| Заказы | Создание заказа, его статусы, координация резервирования и оплаты |
| Платежи | Расчёт суммы списания и комиссии, учёт платежей и возвратов, работа с провайдером |
| Уведомления | Отправка сообщений о статусах заказа и повторные попытки доставки |

Для учебной модели приняты RUB, комиссия 5%, один платёж за заказ и уведомления
по email. Персонализация учитывает интересы и просмотры без ML; при оформлении
заказа цены и наличие повторно проверяются в Catalog.

### Распределение доменов по сервисам

Каждому домену соответствует отдельный сервис:

| Домен | Сервис |
| --- | --- |
| Пользователи | Users |
| Каталог | Catalog |
| Персонализированная лента | Feed |
| Заказы | Orders |
| Платежи | Payments |
| Уведомления | Notifications |

Web App и API Gateway выполняют технические задачи и не выделяются в бизнес-домены.
Стек: React + TypeScript, Nginx, Rust, PostgreSQL 17 и RabbitMQ 4.
Каркас Orders использует Axum и Tokio.

- Users объединяет покупателей и продавцов: один аккаунт может иметь обе роли,
  поэтому отдельные сервисы аутентификации не нужны.
- Catalog хранит карточки, цены и остатки вместе, чтобы публикация товаров
  и резервирование выполнялись в локальных транзакциях.
- Feed отделён от Catalog, чтобы частые чтения и пересчёт ленты масштабировались
  независимо от операций продавцов.
- Orders и Payments разделены, поскольку жизненный цикл заказа и движение денег
  требуют разных проверок, прав доступа и способов восстановления.
- Notifications выделен отдельно, чтобы сбой доставки писем не блокировал
  оформление и оплату заказа.

### Границы владения данными и взаимодействия

| Сервис | Собственные данные |
| --- | --- |
| Users | Аккаунты, хеши паролей, роли, адреса, контакты, интересы и согласия на уведомления |
| Catalog | Карточки товаров, идентификаторы продавцов, цены, остатки и резервы |
| Feed | Локальная проекция каталога и интересов, статистика просмотров |
| Orders | Заказы, покупатели и продавцы в заказе, снимки названий и цен, адрес доставки, итоговая сумма и статусы |
| Payments | Платёжные попытки, суммы, валюта, комиссия, финансовые записи и идентификаторы провайдера |
| Notifications | Шаблоны, задания и история доставки; актуальные контакты получает из Users |

У каждого сервиса отдельная БД PostgreSQL и собственные учётные данные.
Только сервис-владелец читает и изменяет свои таблицы. Общих БД и прямого доступа
к чужим таблицам нет; сервисы обмениваются данными через API и события,
ссылаясь на сущности по ID.

Catalog остаётся источником актуальных цен и остатков. Orders хранит снимок
товара на момент заказа, а Feed хранит локальную проекцию для ленты. Web App и Gateway
не владеют доменными данными, RabbitMQ хранит сообщения. Карточные реквизиты
хранит внешний платёжный провайдер.

#### Взаимодействия

| Инициатор → получатель | Способ | Назначение |
| --- | --- | --- |
| Покупатель/продавец → Web App | Синхронно, HTTPS | Работа в браузере |
| Web App → Gateway | Синхронно, HTTPS/JSON | Единая точка входа API |
| Gateway → Users | Синхронно, HTTP/JSON во внутренней сети | Вход, профиль, роли, интересы |
| Gateway → Catalog | Синхронно, HTTP/JSON | Карточки товаров и операции продавца |
| Gateway → Feed | Синхронно, HTTP/JSON | Лента и регистрация просмотра |
| Gateway → Orders | Синхронно, HTTP/JSON | Оформление и получение статуса заказа |
| Gateway → Payments | Синхронно, HTTP/JSON | Статус и ссылка на оплату, проксирование webhook |
| Orders → Catalog | Синхронно, HTTP/JSON | Проверить цены, зарезервировать, подтвердить/освободить резерв |
| Orders → Users | Синхронно, HTTP/JSON | Проверить покупателя и получить адрес |
| Notifications → Users | Синхронно, HTTP/JSON | Получить актуальный email и разрешённый способ уведомления |
| Payments → платёжный провайдер | Синхронно, HTTPS/JSON | Создать платёж, запросить статус, инициировать возврат |
| Провайдер → Gateway → Payments | Асинхронный callback, HTTPS → HTTP/JSON | Сообщить результат платежа |
| Notifications → email-провайдер | Синхронно, HTTPS API | Передать сообщение для доставки |
| Catalog → RabbitMQ → Feed | Асинхронно, AMQP | Обновить проекцию каталога |
| Users → RabbitMQ → Feed | Асинхронно, AMQP | Обновить интересы пользователя |
| Orders → RabbitMQ → Payments | Асинхронно, AMQP | Создать или отменить платёж, запросить возврат |
| Payments → RabbitMQ → Orders | Асинхронно, AMQP | Сообщить об оплате, отказе или возврате |
| Orders → RabbitMQ → Notifications | Асинхронно, AMQP | Сообщить об изменении статуса заказа |

Orders координирует резервирование и оплату заказа, Payments сообщает результат
платежа, Notifications отправляет уведомление. При отмене заказа резерв
освобождается, а полученная оплата возвращается.

Между сервисами допускается задержка обновления данных. Для обработки сбоев
предусмотрены повторы, идемпотентность, outbox и дедупликация событий.
Эти механизмы пока не реализованы.

### Альтернативные варианты декомпозиции

#### Вариант A: модульный монолит

Один backend с модулями Users, Catalog, Feed, Orders, Payments и Notifications,
одна PostgreSQL с отдельными схемами модулей и фоновый worker. Модули вызывают
друг друга внутри процесса. Общая БД принадлежит одному сервису.

#### Вариант B: шесть доменных сервисов (выбран)

Users, Catalog, Feed, Orders, Payments и Notifications развёртываются независимо.
У каждого своя БД; запросы идут по HTTP, события через RabbitMQ.

### Trade-off’ы вариантов

#### Вариант A: модульный монолит

Плюсы:

- Один релиз, простой локальный запуск и меньше инфраструктуры.
- Создание заказа и резервирование можно выполнить в одной транзакции.
- Ниже затраты на эксплуатацию для небольшой команды.

Минусы:

- Рост нагрузки на ленту требует масштабировать весь backend.
- Тяжёлый пересчёт ленты может затронуть оформление заказов.
- Изменение платёжной интеграции требует релиза всего приложения;
  финансовые данные изолированы преимущественно на уровне кода и прав доступа.

#### Вариант B: шесть доменных сервисов

Плюсы:

- Feed масштабируется независимо от каталога и заказов.
- Очередь изолирует сбои доставки уведомлений от оформления заказа.
- Финансовые данные и ключи платёжного провайдера доступны только Payments.
- Сервисы можно разрабатывать и выпускать независимо.

Минусы:

- Шесть БД и брокер повышают затраты на эксплуатацию и мониторинг.
- Оформление заказа затрагивает несколько сервисов: нужны компенсации,
  повторы и защита от повторной обработки событий.
- Лента и статусы обновляются с задержкой; сквозная отладка и тестирование сложнее.
- Новый заказ зависит от доступности Users, Gateway остаётся общей точкой входа.

### Обоснование финального выбора

Выбран вариант B: лента и каталог имеют разные профили нагрузки, сбои внешних
провайдеров оплаты и email требуют изоляции. Финансовому учёту нужен отдельный
владелец данных. Эти задачи определяют границы сервисов.

На этапе ДЗ 1 был реализован только каркас Orders без бизнес-логики.
Дополнительные сервисы Search, Inventory и ML-платформа пока не нужны.
Вариант B сложнее в эксплуатации; для небольшого MVP с одной командой
разумнее начать с монолита и выделять сервисы по мере роста нагрузки.


### Переход к ДЗ 2

В ДЗ 2 реализовано транзакционное ядро: Auth, Catalog и Orders — модули одного
Rust-приложения, которому принадлежит одна PostgreSQL. Таблицы заказов,
остатков и промокодов изменяются в одной локальной ACID-транзакции.
Разнесение этих данных по сервисам потребовало бы saga с компенсациями или 2PC;
saga не обеспечивает требуемый атомарный откат, а 2PC усложняет этот учебный этап.
Поэтому отдельные Payments, Feed, Notifications и RabbitMQ остаются частью
целевой архитектуры ДЗ 1 и пока не реализованы. Это осознанное изменение
декомпозиции для ДЗ 2; общих БД между независимо работающими сервисами нет.
