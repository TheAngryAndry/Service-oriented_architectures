# Маркетплейс: архитектура C4 и каркас сервиса

Учебный проект по сервис-ориентированной архитектуре маркетплейса. Продавцы
публикуют товары, а покупатели просматривают персонализированную ленту,
оформляют и оплачивают заказы, получают уведомления об их статусах.

Реализован только каркас Orders на Rust: HTTP-сервер, `GET /health` и Docker-образ.
Остальные сервисы и бизнес-логика описаны как целевая архитектура.

## 1. Базовая C4-диаграмма

![C4 Container: архитектура маркетплейса](docs/architecture/container.png)

[Открыть полную диаграмму](docs/architecture/container.png)

Диаграмма уровня C4 Container показывает границу маркетплейса, пользователей,
внешние системы, приложения, брокер и хранилища. У контейнеров указаны название,
тип, технология и ответственность, у связей направление, назначение и протокол.

Модель разделена на два вида: запросы и данные сверху, события через RabbitMQ
снизу. Повторяющиеся сервисы обозначают одни и те же контейнеры. Сплошные линии
показывают синхронные вызовы, пунктир обозначает асинхронные взаимодействия.

## 2. Сервис в Docker и ответ 200 OK

Нужны запущенный Docker, Docker Compose v2 с поддержкой `up --wait` и свободный
порт 8080. Выполните из корня проекта:

```sh
docker compose up --build -d --wait --wait-timeout 60
curl -i http://localhost:8080/health
```

Сервис должен вернуть `200 OK` и тело ответа:

```json
{"status":"ok"}
```

Остановка:

```sh
docker compose down
```

## 3. Домены и их ответственность

| Домен | Ответственность |
| --- | --- |
| Пользователи | Регистрация, вход, роли покупателя и продавца, профиль и предпочтения |
| Каталог | Публикация товаров, категории, актуальные цены, остатки и резервирование |
| Персонализированная лента | Ранжирование и выдача товаров по предпочтениям и просмотрам |
| Заказы | Создание заказа, его статусы, координация резервирования и оплаты |
| Платежи | Расчёт суммы списания и комиссии, учёт платежей и возвратов, работа с провайдером |
| Уведомления | Отправка сообщений о статусах заказа и повторные попытки доставки |

Для учебной модели приняты RUB, комиссия 5%, один платёж за заказ и уведомления
по email. Персонализация учитывает интересы и просмотры без ML; при оформлении
заказа цены и наличие повторно проверяются в Catalog.

## 4. Распределение доменов по сервисам

Каждому домену соответствует отдельный сервис:

| Домен | Сервис |
| --- | --- |
| Пользователи | Users |
| Каталог | Catalog |
| Персонализированная лента | Feed |
| Заказы | Orders |
| Платежи | Payments |
| Уведомления | Notifications |

Web App и API Gateway выполняют технические задачи и не выделяются в бизнес-домены.
Стек: React + TypeScript, Nginx, Rust, PostgreSQL 17 и RabbitMQ 4.
Каркас Orders использует Axum и Tokio.

- Users объединяет покупателей и продавцов: один аккаунт может иметь обе роли,
  поэтому отдельные сервисы аутентификации не нужны.
- Catalog хранит карточки, цены и остатки вместе, чтобы публикация товаров
  и резервирование выполнялись в локальных транзакциях.
- Feed отделён от Catalog, чтобы частые чтения и пересчёт ленты масштабировались
  независимо от операций продавцов.
- Orders и Payments разделены, поскольку жизненный цикл заказа и движение денег
  требуют разных проверок, прав доступа и способов восстановления.
- Notifications выделен отдельно, чтобы сбой доставки писем не блокировал
  оформление и оплату заказа.

## 5. Границы владения данными и взаимодействия

| Сервис | Собственные данные |
| --- | --- |
| Users | Аккаунты, хеши паролей, роли, адреса, контакты, интересы и согласия на уведомления |
| Catalog | Карточки товаров, идентификаторы продавцов, цены, остатки и резервы |
| Feed | Локальная проекция каталога и интересов, статистика просмотров |
| Orders | Заказы, покупатели и продавцы в заказе, снимки названий и цен, адрес доставки, итоговая сумма и статусы |
| Payments | Платёжные попытки, суммы, валюта, комиссия, финансовые записи и идентификаторы провайдера |
| Notifications | Шаблоны, задания и история доставки; актуальные контакты получает из Users |

У каждого сервиса отдельная БД PostgreSQL и собственные учётные данные.
Только сервис-владелец читает и изменяет свои таблицы. Общих БД и прямого доступа
к чужим таблицам нет; сервисы обмениваются данными через API и события,
ссылаясь на сущности по ID.

Catalog остаётся источником актуальных цен и остатков. Orders хранит снимок
товара на момент заказа, а Feed хранит локальную проекцию для ленты. Web App и Gateway
не владеют доменными данными, RabbitMQ хранит сообщения. Карточные реквизиты
хранит внешний платёжный провайдер.

### Взаимодействия

| Инициатор → получатель | Способ | Назначение |
| --- | --- | --- |
| Покупатель/продавец → Web App | Синхронно, HTTPS | Работа в браузере |
| Web App → Gateway | Синхронно, HTTPS/JSON | Единая точка входа API |
| Gateway → Users | Синхронно, HTTP/JSON во внутренней сети | Вход, профиль, роли, интересы |
| Gateway → Catalog | Синхронно, HTTP/JSON | Карточки товаров и операции продавца |
| Gateway → Feed | Синхронно, HTTP/JSON | Лента и регистрация просмотра |
| Gateway → Orders | Синхронно, HTTP/JSON | Оформление и получение статуса заказа |
| Gateway → Payments | Синхронно, HTTP/JSON | Статус и ссылка на оплату, проксирование webhook |
| Orders → Catalog | Синхронно, HTTP/JSON | Проверить цены, зарезервировать, подтвердить/освободить резерв |
| Orders → Users | Синхронно, HTTP/JSON | Проверить покупателя и получить адрес |
| Notifications → Users | Синхронно, HTTP/JSON | Получить актуальный email и разрешённый способ уведомления |
| Payments → платёжный провайдер | Синхронно, HTTPS/JSON | Создать платёж, запросить статус, инициировать возврат |
| Провайдер → Gateway → Payments | Асинхронный callback, HTTPS → HTTP/JSON | Сообщить результат платежа |
| Notifications → email-провайдер | Синхронно, HTTPS API | Передать сообщение для доставки |
| Catalog → RabbitMQ → Feed | Асинхронно, AMQP | Обновить проекцию каталога |
| Users → RabbitMQ → Feed | Асинхронно, AMQP | Обновить интересы пользователя |
| Orders → RabbitMQ → Payments | Асинхронно, AMQP | Создать или отменить платёж, запросить возврат |
| Payments → RabbitMQ → Orders | Асинхронно, AMQP | Сообщить об оплате, отказе или возврате |
| Orders → RabbitMQ → Notifications | Асинхронно, AMQP | Сообщить об изменении статуса заказа |

Orders координирует резервирование и оплату заказа, Payments сообщает результат
платежа, Notifications отправляет уведомление. При отмене заказа резерв
освобождается, а полученная оплата возвращается.

Между сервисами допускается задержка обновления данных. Для обработки сбоев
предусмотрены повторы, идемпотентность, outbox и дедупликация событий.
Эти механизмы пока не реализованы.

## 6. Альтернативные варианты декомпозиции

### Вариант A: модульный монолит

Один backend с модулями Users, Catalog, Feed, Orders, Payments и Notifications,
одна PostgreSQL с отдельными схемами модулей и фоновый worker. Модули вызывают
друг друга внутри процесса. Общая БД принадлежит одному сервису.

### Вариант B: шесть доменных сервисов (выбран)

Users, Catalog, Feed, Orders, Payments и Notifications развёртываются независимо.
У каждого своя БД; запросы идут по HTTP, события через RabbitMQ.

## 7. Trade-off’ы вариантов

### Вариант A: модульный монолит

Плюсы:

- Один релиз, простой локальный запуск и меньше инфраструктуры.
- Создание заказа и резервирование можно выполнить в одной транзакции.
- Ниже затраты на эксплуатацию для небольшой команды.

Минусы:

- Рост нагрузки на ленту требует масштабировать весь backend.
- Тяжёлый пересчёт ленты может затронуть оформление заказов.
- Изменение платёжной интеграции требует релиза всего приложения;
  финансовые данные изолированы преимущественно на уровне кода и прав доступа.

### Вариант B: шесть доменных сервисов

Плюсы:

- Feed масштабируется независимо от каталога и заказов.
- Очередь изолирует сбои доставки уведомлений от оформления заказа.
- Финансовые данные и ключи платёжного провайдера доступны только Payments.
- Сервисы можно разрабатывать и выпускать независимо.

Минусы:

- Шесть БД и брокер повышают затраты на эксплуатацию и мониторинг.
- Оформление заказа затрагивает несколько сервисов: нужны компенсации,
  повторы и защита от повторной обработки событий.
- Лента и статусы обновляются с задержкой; сквозная отладка и тестирование сложнее.
- Новый заказ зависит от доступности Users, Gateway остаётся общей точкой входа.

## 8. Обоснование финального выбора

Выбран вариант B: лента и каталог имеют разные профили нагрузки, сбои внешних
провайдеров оплаты и email требуют изоляции. Финансовому учёту нужен отдельный
владелец данных. Эти задачи определяют границы сервисов.

Для учебного задания реализован только каркас Orders без бизнес-логики.
Дополнительные сервисы Search, Inventory и ML-платформа пока не нужны.
Вариант B сложнее в эксплуатации; для небольшого MVP с одной командой
разумнее начать с монолита и выделять сервисы по мере роста нагрузки.
